# agentlab.fun 网站运营方案

**版本**：2026-06-01  
**目标**：把 agentlab.fun 运营成一个围绕 Agent Runtime、AI 编程和工具调用治理的个人技术站，而不是只按日期堆文章的博客。

---

## 一、网站定位

agentlab.fun 的定位应当收窄到一句话：

> 记录 Agent 系统、AI 编程和人机协作的长期技术判断。

这个站的优势不是资讯速度。资讯站会被大平台压住，也容易变成搬运。这里更适合做三类内容：

1. **概念定义**：把 Agent、Runtime、Skill、Tool Call、Context、Action 这些词讲清楚。
2. **工程判断**：解释 AI 编程为什么会放大烂项目、工具调用为什么会污染上下文、Runtime 为什么要接管状态。
3. **长期索引**：把零散文章沉淀到专题页，让读者和搜索引擎知道这个站在持续研究什么。

判断一篇内容是否该发，问三个问题：

- 它能不能解释一个具体技术现象？
- 它能不能沉淀到某个专题页？
- 三个月后再读，它还有没有参考价值？

三个问题都答不上来，就不要放到博客主线，可以放进草稿或 insight 素材池。

---

## 二、内容结构

当前站点应该按四层运营。

### 2.1 首页

首页负责回答两个问题：

- 这个人长期研究什么？
- 哪几篇文章最能代表这个站？

首页不应该只展示最新文章。建议保留少量精选内容，优先展示：

- Agent Runtime
- Tool Calling
- AI Coding
- Agent 实验

首页更新频率：每月一次。只在代表文章变化、专题页变化、站点定位变化时更新。

### 2.2 专题页

专题页是这个站最重要的 SEO 和 AI 搜索入口。当前已有：

- `/topics/agent-runtime/`
- `/topics/tool-calling/`
- `/topics/ai-coding/`

建议继续补两个专题：

- `/topics/agent-product/`：Agent 产品形态、用户交互、任务边界
- `/topics/ai-workflow/`：AI 工作流、个人自动化、协作方式

专题页不是文章列表。每个专题页要有：

- 一段 100-200 字的主题说明
- 5-8 篇代表文章
- 3-5 条可引用结论
- 相关术语解释
- 最近一次更新时间

专题页更新频率：每两周一次。

### 2.3 博客

博客负责发表完整观点。建议分成三种文章：

| 类型 | 目标 | 频率 | 长度 |
|---|---|---:|---:|
| 定义文 | 解释一个概念 | 每周 1 篇 | 1200-2500 字 |
| 判断文 | 对一个技术趋势下判断 | 每周 1 篇 | 1500-3000 字 |
| 案例文 | 拆一个具体系统或实践 | 每两周 1 篇 | 2000-4000 字 |

标题要像读者会搜索的问题。比如：

- `Agent Runtime 是什么：为什么不能只靠 Tool Call Loop`
- `AI 编程为什么会放大烂项目的问题`
- `Tool Call 噪音从哪里来：一次 Agent 执行链路拆解`

少用只表达情绪的标题。标题要给搜索引擎和读者一个明确入口。

### 2.4 Insights

Insights 是素材池，不是主阵地。它适合放：

- 外部文章摘录和判断
- 新产品、新论文、新框架的短评
- 以后可能扩展成博客的种子

每条 insight 最好都标出：

- 来源链接
- 原文在说什么
- 对本站主题有什么关系
- 是否值得扩展成博客

Insights 更新频率可以高一点，但不要让它抢走博客和专题页的维护时间。

## 三、发布节奏

建议采用固定节奏，避免靠灵感驱动。

### 每周

- 写 1 篇博客主文。
- 发 2-3 条 insights。
- 把新文章补到相关专题页。
- 检查首页精选是否需要替换。
- 发布后在 2-3 个渠道分发。

### 每两周

- 更新一次专题页。
- 检查站内链接：新文章至少链接 2 篇旧文，旧专题页链接新文。
- 从 insights 里挑 1 条扩展成博客。

### 每月

- 做一次内容复盘：
  - 哪些主题写得最多？
  - 哪些文章值得放到首页？
  - 哪些文章标题太弱，需要重命名或补 description？
  - 哪些专题页缺代表文章？
- 检查 Search Console / Bing Webmaster 的索引情况。
- 检查 `sitemap.xml`、`feed.xml`、`llms.txt`、`robots.txt`。

## 四、选题策略

这个站的选题不要追“今天哪个模型发布了”。更适合围绕问题写。

### 4.1 核心问题池

优先写这些问题：

- Agent 和普通 Workflow 的边界在哪里？
- Runtime 应该负责哪些事，模型应该负责哪些事？
- Tool Call 的中间结果为什么会变成上下文噪音？
- AI 编程为什么能写代码，却救不了坏需求？
- 多 Agent 协作什么时候有用，什么时候只是制造复杂度？
- Agent 产品怎么设计权限、状态、恢复和确认？
- 面向 AI 搜索的网页应该怎么组织信息？

### 4.2 文章模板

每篇主文按这个结构写：

1. 一个具体场景开头。
2. 说清楚问题为什么出现。
3. 拆成 2-4 个可理解的机制。
4. 给出判断边界：什么情况下成立，什么情况下不成立。
5. 链接到相关旧文或专题页。
6. 结尾给一个可执行判断，而不是口号。

不要写成空泛的趋势宣言。读者更需要能带走的判断。

## 五、分发渠道

站点本身负责沉淀，外部渠道负责带人回来。

### 5.1 GitHub

适合发布偏工程的内容：

- Agent Runtime 设计
- Tool Call / Action 抽象
- AI 编程质量
- Harness / Protocol 设计

动作：

- 在相关项目 README 里链接代表文章。
- 有代码实践时，把文章作为设计背景链接到 PR 或 docs。
- 每月整理一次“Agent 系统设计文章索引”。

### 5.2 公众号

适合发布更完整的中文长文。每篇公众号文末都放：

- 原文链接
- 相关专题页
- 个人网站入口

公众号标题可以更口语，但原站标题要保留搜索友好。

### 5.3 X / 即刻 / 掘金 / 知乎

不要全文搬运。建议每篇文章拆成 3 种分发素材：

- 一条 200 字摘要
- 一张核心图或金句图
- 一个具体争议点

外部平台负责给出钩子，完整阅读尽量回到专题页。

## 六、SEO 和 AI 搜索

已经完成的基础设施：

- `sitemap.xml`
- `feed.xml`
- `llms.txt`
- `robots.txt`
- canonical
- Open Graph
- Article JSON-LD
- 专题页

接下来要做的是内容层 SEO。

### 6.1 每篇文章的元数据

新文章建议都有：

```yaml
title:
description:
date:
tags:
permalink:
```

`description` 不要复述标题，要回答“这篇文章解决什么问题”。长度控制在 80-160 字。

### 6.2 内链规则

每篇博客至少有 3 个站内链接：

- 1 个链接到专题页
- 1 个链接到前序文章
- 1 个链接到后续阅读或相关案例

专题页每次更新时，把新文章补进去。不要只让文章进入 `/blog/` 时间线。

### 6.3 AI 搜索可读性

给 AI 搜索看的页面要更直接：

- 开头 200 字说清楚主题。
- 小标题用问题或明确概念。
- 结论不要藏在最后。
- 重要定义用稳定措辞。
- 避免把关键内容只放在图片里。

`llms.txt` 每月检查一次，确保代表文章还是当前最强内容。

## 七、指标

不要一开始盯总访问量。先看内容资产有没有变强。

### 7.1 每周指标

- 新增主文数量
- 新增 insight 数量
- 新增站内链接数量
- 专题页是否更新
- 是否完成外部分发

### 7.2 每月指标

- Google Search Console 收录页数
- Bing Webmaster 收录页数
- 搜索点击最多的 10 个页面
- 被 AI 搜索或外部平台引用的页面
- 首页和专题页是否带来更多入口流量

### 7.3 内容质量指标

每月挑 5 篇文章复查：

- 标题是否像搜索问题？
- 开头是否说明具体场景？
- 是否有清楚结论？
- 是否链接到专题页？
- 是否值得一年后继续保留？

## 九、运营原则

1. **少追热点，多造概念入口。** 热点会过期，概念入口会长期被搜索。
2. **文章写完不是结束，要进入专题页。** 没有进入专题页的文章，很快会被时间线埋掉。
3. **先讲清楚问题，再表达立场。** 观点可以锋利，但要落到场景和机制。
4. **把 insight 当素材，不当成果。** 更耐用的资产是主文、专题页和可引用结论。
5. **站点服务长期记忆。** 外部平台负责传播，agentlab.fun 负责沉淀。
